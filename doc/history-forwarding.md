# 历史未读邮件补转

管理员可在「系统设置 → 邮件推送 → 历史未读邮件补转」中，将自己邮箱里保存的历史未读邮件补发到已配置的第三方邮箱。

## 使用步骤

1. 在「第三方邮箱」中保存目标地址并启用转发。目标地址必须已在当前 Cloudflare 账户的 Email Routing → Destination Addresses 中验证。
2. 打开「历史未读邮件补转」，选择自己的邮箱和收件时间范围。留空时间范围会检查所有符合条件的历史未读邮件。
3. 点击「预览」，核对待补转数量、目标地址和发件服务状态。
4. 点击确认补转，阅读确认框中的数量和目标后开始发送。
5. 查看发送进度。可暂停、继续，或在「补转记录」中查看最近 20 次任务。明确失败的项目可以手动重试。

关闭弹窗或刷新页面会停止发起下一批，已经开始的一批仍可能完成。重新打开后查看任务状态，再点击继续。发生网络中断时，先刷新状态；投递结果未知的项目不会自动重发，应到目标邮箱核对。

## 邮件内容与范围

- 只处理当前管理员拥有的邮箱中，未删除、已完整收取、仍未读的收件邮件，并遵守当前转发规则。
- 开始任务时固定历史范围，预览之后新增的邮件不会被纳入此次补转。发送前还会核对原邮件的未读状态和邮箱归属。
- 原邮件继续保留，未读状态不会因补转而改变。
- 目标邮箱收到一封新邮件，主题为 `Fwd: 原主题`，发件地址使用原站内收件邮箱。正文注明原发件人、原收件人和收件时间；回复地址指向原发件人。
- 补发包含已保存的正文、普通附件和内嵌图片。无法完整恢复未保存的原始邮件头和认证签名。附件缺失时整封停止发送并显示原因。
- 每次最多 1000 封邮件、2000 次投递，每批最多 3 次投递。Cloudflare 通道每批最多 3 条并行发送；Resend 通道保持串行及每条发送后 700ms 间隔。页面批次间等待为 100ms，暂停在当前批次完成后生效。邮件大小按编码后的 5 MiB 上限保守检查，最多 32 个附件。

## 去重与结果

补转成功的「原邮件 + 目标地址」会记录到数据库。再次预览时会跳过这些记录。新版本之后自动转发成功的邮件也会记录并跳过。

功能上线之前没有保存转发结果的旧邮件，无法判断是否曾转发过。请按实际需要选择时间范围，避免重复收到旧邮件。

页面「发送成功」表示发件服务已接受邮件，实际是否进入收件箱还需检查目标邮箱（包含垃圾邮件）。有 Resend 投递回执时，后台也会保存相应状态。结果未知的发送不会自动重试，以免重复投递。

## 部署与验证

新增 `backfill_email` 专用 Cloudflare 发件绑定，用于补转到当前账户已验证的目标地址。普通发件服务的选择保持原配置；也兼容现有 `email` 绑定或所选域名的 Resend Token。

继续使用现有 Worker 名称、D1、KV、R2 和域名配置。新表和索引均使用 `IF NOT EXISTS`，在管理员首次打开功能或新邮件成功自动转发时增量创建；现有数据库升级入口也包含相同升级步骤。升级不会重建或清空原邮件和附件表。

Cloudflare Workers Builds 的根目录使用 `/mail-worker`，Production 和 Previews Base 的 Build command 均设置为：

```sh
pnpm --prefix ../mail-vue install --frozen-lockfile && pnpm --prefix ../mail-vue run build
```

生产 Deploy command 使用 `npx wrangler deploy`。当前项目关闭了公开预览地址，Previews Base 的 Preview command 使用 `npx wrangler deploy --dry-run`，让功能分支完成打包验证。合并到生产分支后更新正式服务。

本地业务验证：

```sh
cd mail-worker
pnpm install --frozen-lockfile
pnpm run test:backfill
```

测试使用本地 SQLite，发件服务均被模拟，不会发送真实邮件。原有 `pnpm test` 是部署脚本，不作为本地业务测试使用。

前端验证：

```sh
cd mail-vue
pnpm install --frozen-lockfile
pnpm run build
```
